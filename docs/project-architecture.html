Reference Architecture · Phase 04

AMC RFP & Portfolio Insight Orchestrator

A multi-agent AI system that drafts institutional RFP responses from live fund data and manager commentary, and puts every draft through an automated, self-correcting compliance review before it reaches a client — hosted on Amazon Bedrock AgentCore, provisioned with Terraform, shipped through a GitHub Actions pipeline.

Strands Agents graph AgentCore Runtime + Gateway + Memory AgentCore Policy — opt-in, blocked upstream Terraform · dev / staging / prod GitHub Actions · OIDC

01System architecture

One request, traced end to end: how a question becomes a compliant answer, and the one setting that decides whether tools run in-process or through a governed gateway.

02Agent orchestration

Five agents as nodes in a graph, not five independent prompts. The compliance judge never drafts, and a draft can only reach the client through one of two explicit, code-gated exits.

Why an independent judge

compliance_check is a separate agent role from the two drafting agents, using structured_output_model to force a typed verdict rather than free text — it evaluates the combined draft against a written rubric (six rules, including a dedicated grounding rule added after a real fabrication incident, see §10) and never contributes prose of its own. A single agent grading its own writing is a weaker control than a separately-prompted reviewer with a fixed rubric and a typed output contract.

03Data layer

Every environment answers from real tool output, never model memory. Which store backs those tools is one setting, not a code fork.

04Amazon Bedrock AgentCore platform

Four managed AgentCore primitives, adopted one phase at a time rather than all at once — each with a real, load-bearing job, not just because it existed.

ComponentStatusRole in this system
Runtime Live Serverless host for the containerized agent graph (ARM64/Graviton, public network mode — VPC mode hits an open, unresolved AWS provider issue with stuck ENIs). Environment variables select model provider, data backend, tool backend, and memory backend per deployment.
Gateway Live · opt-in MCP-protocol, IAM/SigV4-authenticated tool router in front of two Lambda targets — lets tool execution be governed and audited centrally instead of living in-process inside the agent container. See Fig. 4.
Memory Live-verified Session-scoped event store with a semantic retrieval strategy — gives the graph real cross-turn continuity without the framework's own graph primitive supporting a session manager directly. See Fig. 5.
Policy Built · blocked upstream Cedar-based, allow-list authorization in front of the Gateway. Infrastructure and code are complete and applied cleanly, but even the documented-safe LOG_ONLY mode currently fails every real tool call with a generic platform error — kept detached (enable_policy=false) so the working Gateway path isn't put at risk chasing it further.

05Infrastructure as code

Terraform, one root module per environment, applied in three deliberate passes — some resources genuinely cannot exist before their prerequisites do.

Environment isolation

dev / staging / prod share one AWS account, isolated by resource-name prefix and separate Terraform state — not separate accounts. dev alone may opt into the cheaper S3 Vectors backend and Ollama; staging/prod are hard-locked to OpenSearch Serverless and Bedrock via Terraform validation blocks, a plan-time error rather than a silent override.

06CI/CD pipeline

Two workflows with deliberately different trust levels — one runs on every pull request and can never touch AWS state; the other only runs on a human's explicit say-so.

Build once, promote everywhere

dev is the only environment that builds a fresh image from source, tagged with the git SHA. staging and prod copy that exact image by digest — no rebuild — so what passed validation in dev is byte-identical to what ships further up. No auto-deploy on merge anywhere, and no required-reviewer gate (a single-maintainer setup would deadlock on approving its own deploy) — the manual trigger plus branch restriction is the safety net instead.

07Security model

No long-lived credentials anywhere in the system, application or pipeline.

  • Application → AWS: IAM roles + SigV4 signing throughout — Gateway and Runtime auth is IAM, not Cognito/JWT.
  • CI → AWS: GitHub's OIDC provider issues a short-lived token per job; AWS trusts it via AssumeRoleWithWebIdentity, scoped to the exact org/repo and, for deploy roles, the exact GitHub Environment claim.
  • Least privilege by naming convention: each deploy-<env> role's permissions are scoped to that environment's resource-name prefix wherever the target service's ARN format allows it.
  • No secrets committed: per-environment config lives in gitignored .env/backend.hcl files; tracked tfvars hold no credentials.

09Evolution by phase

Four phases, each adding one architectural layer on a working foundation — never a rewrite.

Phase 01

Core agentic system

The 5-agent compliance graph, built and proven entirely locally — Ollama, SQLite, ChromaDB, REST API, CLI, full test suite.

Phase 02

Cloud deployment

Same logic, containerized onto AgentCore Runtime. Terraform-provisioned DynamoDB and Bedrock Knowledge Base replace the local stores.

Phase 03

CI/CD pipeline

GitHub Actions, OIDC federated auth, PR validation, and the build-once / promote-everywhere deployment model.

Phase 04

Advanced capabilities

Gateway-routed tool calling, AgentCore Memory continuity, an anti-fabrication grounding fix, and a Cedar policy layer (built, currently blocked upstream).

11Current status

Cost discipline over always-on infrastructure

This is a personal/portfolio project, not a production tenant — cloud environments are deliberately torn down between working sessions rather than left running, and rebuilt from the same Terraform + CI/CD path described above. The architecture on this page is the standing design; live AWS state at any given moment should be confirmed independently rather than assumed from this document.
